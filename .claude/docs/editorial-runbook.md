# 編集部ランブック(学習コンテンツの企画・執筆・校閲・出版)

トレンド(ニュース)の自動更新とは**別系統**の仕組み。恒常ページ(`content/pages/**`)を
AIエージェントの「編集部」が組織的に増やし・磨くための手順書。

- ニュースの定期更新 → `update-runbook.md`(1日おき・自動デプロイ)
- 学習コンテンツの編集 → **このドキュメント**(人間の承認を経て公開)

## 0. 原則

- **本番は人間の承認なしに変えない。** 成果物はブランチに出し、プレビューURLで確認 → 承認 → main にマージ。
- 執筆様式・スキーマ・専門用語ルールは `.claude/docs/content-guide.md` が正(全員が必ず読む)。
- 打ち切り/連載順位のような競争機構は入れない。目的は蔵書を増やし品質を上げること。
- テーマ台帳 `.claude/docs/editorial/themes.json` を記憶として使う(企画の重複防止・進捗管理)。

## 1. 編成(役割)

| 役割 | 仕事 |
|---|---|
| 編集長 | テーマ選定と優先順位づけ。既存ページとの重複回避。台帳の更新 |
| リサーチャー | 一次情報の調査(公式ドキュメント・論文・実測)。事実と出典の確保 |
| 執筆者 | content-guide 準拠でページJSONを執筆(テーマごとに並列) |
| 校閲①(事実) | 数値・名称・日付の裏取り。裏の取れない記述は削るか「未確認」と明記させる |
| 校閲②(読者) | オカン基準の点検。説明もリンクも無い専門用語を全数で潰す。冗長さを削る |
| 品質ゲート | `python3 tools/validate.py` + ヘッドレスブラウザで描画確認 |

## 2. 進行

1. **企画会議** — 編集長が台帳と `content/site.json` を読み、次に出すページ(slug/title/summary)を決める。
   判断軸: (a) 読者が詰まる順序上の穴 (b) 実務での使用頻度 (c) 既存ページとの重複がないこと。
2. **台帳更新** — `.claude/docs/editorial/themes.json` に採用テーマを `planned` で追加。
3. **site.json 更新** — 決定した slug/title/summary をナビに登録(実体がないと検証が落ちるので執筆と同じ回で行う)。
4. **執筆** — テーマごとに並列。1テーマ1ファイル。他テーマのファイルや共有ファイルは触らない。
   - **共有ファイル(`content/glossary.json`, `content/site.json`)は執筆者が直接編集しない。**
     新しい用語が必要なら「追加してほしい用語」として報告し、編集長(または人間)がまとめて追加する。
5. **校閲** — ①事実 → ②読者 の順。校閲者は対象ファイルを直接修正してよい。
6. **検証** — `python3 tools/validate.py` を通す。エラーがあれば直るまで出版しない。
7. **出版(承認つき)**
   ```bash
   git switch -c editorial/<日付>-<テーマ群>
   git add content/ .claude/docs/
   git commit -m "editorial: <内容>"
   git push -u origin editorial/<...>     # 非本番ブランチ = プレビューURLが発行される
   ```
   → **編集部がプレビューURLを算出し、記事への直リンクまで作って人間に提示する。**
   ユーザーにダッシュボードを探させないこと(校了紙は編集部が持っていく)。

   **プレビューURLの規則**(ブランチ名の `/` 等をハイフンに置換 + `-<worker名>.<サブドメイン>`):
   ```
   https://<branch-with-dashes>-antenna-ai.km-solo-developer.workers.dev
   例) editorial/2026-08-24-agent-and-evolution
     → https://editorial-2026-08-24-agent-and-evolution-antenna-ai.km-solo-developer.workers.dev
   ```
   提示前に必ず疎通確認する(ビルドに1〜2分かかるので、200が返るまで待つ):
   ```bash
   P="https://<...>.workers.dev"
   curl -s -o /dev/null -w "%{http_code}\n" "$P/"                    # 200 になるまで待つ
   curl -s "$P/content/site.json" | python3 -m json.tool | head       # 新ページが載っているか
   ```
   提示は「サイト全体のURL」だけでなく、**新規/変更したページへの `#/section/slug` 直リンク**を並べる。
   (ハッシュが長くDNSラベル63文字を超える場合や404の場合のみ、ダッシュボードでの確認手順を案内する)

   → **承認を得てから** `main` にマージして公開。
8. **記録** — 台帳を `published` に更新し、`docs/release-log.md` に記録。

## 3. 品質基準(校閲チェックリスト)

- [ ] 冒頭に例え話がある / 見出しは2〜4節 / 「次のステップ」がある
- [ ] 専門用語に説明かリンクがある(全数)
- [ ] 「なぜ?」に答えている(用語の言い換えで終わっていない)
- [ ] 事実は出典で裏が取れる。不確かなものは書かないか「未確認」と明記
- [ ] Markdown記法(`**`等)を使っていない
- [ ] 図解が有効な箇所で `nested` / `flow` / `demo` を使えているか
- [ ] **字数の上限は設けない**(2026-08-24 撤廃)。短くするために説明を削っていないか
- [ ] 冗長な繰り返し(同じ主張の言い換え・図解の内容の本文での再説明)がないか
